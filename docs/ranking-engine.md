# 순위 엔진 — 서버가 매 턴 하는 일

[질문 API](question-api.md) 왕복 하나가 도착했을 때 서버 안에서 벌어지는 계산이다.
쓰는 재료(적금 데이터)의 모양은 [적금 데이터](savings-data.md)에 있다.

## 세 단계 — 판정 → 순위 → 질문 선별

요청이 올 때마다 서버는 아래 세 단계를 처음부터 다시 돈다. 이전 요청을 기억하지 않으므로 매번 전체를 다시 계산한다.

```
답 전체 도착
→ ① 판정: 모든 상품의 모든 우대조건에 ✅/❌/❓ 를 매긴다
     ✅ 받을 수 있음 (답으로 확인됨) · ❌ 못 받음 · ❓ 아직 몰라서 판단 불가
→ ② 순위: ✅ 만 금리에 반영해 지금 기준 순위를 매긴다
→ ③ 선별: 남은 ❓ 를 하나씩 검사 — "이 ❓ 가 ✅ 로 바뀌면 1위가 뒤집히나?"
     뒤집힐 수 있는 ❓ 가 있다 → 효과가 가장 큰 것의 질문을 응답      (QUESTION)
     하나도 없다           → ② 의 순위가 곧 확정 순위, 결과를 응답  (DONE)
```

핵심 두 가지:

- **순위는 마지막에 한 번 매기는 것이 아니라 매 턴 매긴다.** 순위를 매겨 봐야 "더 물을 값어치가 있는 질문"을 고를 수 있기 때문이다.
  `DONE` 의 최종 순위는 ② 에서 이미 계산돼 있던 것 그대로다.
- **"더 판단할 게 없다" = ❓ 가 0개가 아니라, 남은 ❓ 중 어느 것도 1위를 바꿀 수 없을 때.**
  ❓ 가 10개 남았어도 전부 순위권 밖 상품이거나 역전 불가능한 소수점 우대라면 묻지 않고 끝낸다 — 사용자를 그만큼 덜 괴롭힌다.

답을 바꾸는 "왔다갔다"도 이 구조가 공짜로 처리한다. 뒤로 가서 답을 고치면 다음 요청의 답 전체가 달라진 것뿐이고,
서버는 어차피 매번 ①부터 다시 돌므로 바뀐 답 기준의 질문/순위가 자연스럽게 나온다.

## 사용자를 구별하지 않아도 되는 이유

순위 계산의 재료는 두 가지뿐이다: **적금 데이터**(서버가 가짐, 모두에게 공통)와 **답 전체**(매 요청 본문에 실려 옴).
"누구의 요청인가"는 재료에 없다. 계산기가 `3+5` 를 누가 눌렀는지 몰라도 8 을 내놓는 것과 같다.

사용자 구별(세션 id)이 필요해지는 건 서버가 답을 보관할 때뿐인데, 보관은 클라이언트가 맡기로 했으므로 서랍이 없고, 서랍이 없으니 이름표도 없다.
같은 이유로 동시에 수만 명이 요청해도 요청끼리 섞일 것이 없다.

## AI 를 순위 계산에 쓰지 않는 이유

산수의 정확성·재현성·근거 제시, 셋 다 규칙 엔진만 보장할 수 있기 때문이다. 상세와 AI 가 맡는 몫은 [AI 의 역할](ai-role.md)에 있다.

## 현재 구현과의 대응 — 코드에서 찾을 자리

턴 루프의 세 단계는 모두 서버(`backend/`)에 있다. 클라이언트는 응답을 그리기만 한다.

| 턴 루프의 단계 | 코드 위치 (백엔드) |
|---|---|
| ① 판정 (✅/❌/❓) | `app/model/vo/condition_group_vo.py` · `product_eligibility_vo.py` · `checked_bonus_vo.py` |
| ② 순위 (금리·만기 수령액) | `app/model/vo/product_rate.py` · `maturity_estimate_vo.py` |
| ③ 질문 선별 (1위를 바꿀 ❓ 골라내기) | `app/service/question/question_flow.py` 의 `_next_answer` |
| 턴 전체 조립 | `app/service/question/question_flow.py` 의 `next_step` |
| 질문 문구·선택지 | `app/dto/response/question.py` · `app/constants/question_text.py` |
| 적금 데이터 | 금감원 공시 동기화 (`backend/scripts/sync_disclosure.py`) |
