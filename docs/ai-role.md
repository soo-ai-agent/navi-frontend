# AI 의 역할 — 어디에 쓰고 어디에 쓰지 않나

한 문장으로: **AI 는 사람 말을 데이터로 번역하는 일만 맡고, 돈 계산과 순위에는 손대지 않는다.**

## 경계 — 두 흐름으로 갈린다

```
[흐름 1 — 한 달에 한 번, 미리]              [흐름 2 — 사용자가 쓸 때마다]
공시 수집 → AI 번역 → 검수 → 적금 데이터    답 전체 → 규칙 엔진 → 다음 질문 or 최종 순위
        ↑ AI 는 여기까지                            ↑ AI 호출 없음
```

| | 흐름 1 (AI 있음) | 흐름 2 (AI 없음) |
|---|---|---|
| 언제 도나 | 공시 갱신 때 배치 1회 | 사용자 요청마다 |
| 하는 일 | 공시 원문 → 구조화된 우대조건 | 판정 → 순위 → 질문 선별 |
| 느려도 되나 | 된다 (사용자를 기다리게 하지 않음) | 안 된다 (요청 경로) |
| 틀려도 되나 | 검수가 거른다 | 안 된다 (금융 추천의 신뢰) |
| 문서 | [적금 데이터](savings-data.md) | [순위 엔진](ranking-engine.md) |

## AI 가 맡는 일 — 공시 원문을 구조로 번역

은행 공시의 우대조건은 사람 말로 온다:

```
"1.우리은행 입출식 계좌에서 각 항목별 실적 월 수가 계약기간의 1/2이상인 경우 /
 가.급여/연금 이체:연 0.7%p / 나.공과금 자동이체 출금: 0.3%p / ..."
```

코드는 이 문장을 못 읽는다. 판정 단계가 쓰는 것은 이 문장을 번역한 구조다:

```json
{"type": "SALARY",  "percentagePoint": 0.7, "label": "급여/연금 이체"}
{"type": "AUTOPAY", "percentagePoint": 0.3, "label": "공과금 자동이체"}
```

이 번역이 AI(LLM)의 일이다. 상품 수백 개 × 매달 갱신을 사람이 손으로 옮길 수 없기 때문이다.
사람 말에서 구조를 뽑는 것은 LLM 이 가장 잘하는 일이기도 하다.

우대조건 문구에서 사용자에게 물을 즉석 질문(`q:` 키)을 만드는 것도 같은 번역 작업에 속한다.

## AI 에게 맡기지 않는 일 — 순위 계산

- **산수** — 금리·만기 수령액은 틀리면 안 되는 계산인데, LLM 은 정확성을 보장하지 못한다
- **재현성** — 같은 답에는 언제나 같은 순위가 나와야 하는데, LLM 은 매번 다를 수 있다
- **근거** — "왜 이 상품이 1위인가"를 보여줘야 하는데, 규칙 엔진은 판정 사유(`verdicts`)가 그대로 나오고 LLM 은 못 낸다

자유 입력 해석(은행명 오타, "삼십만원" 같은 금액 표현)은 온라인 AI 의 후보이긴 하다.
다만 지금은 규칙(`bankMatches`·`parseWon`)으로 충분히 돌고 있으므로, 실패 사례가 쌓이면 그때 검토한다.

## 안전장치

- **검수 단계를 거친다** — AI 산출물은 사람 또는 규칙 검증을 통과한 뒤에만 적금 데이터로 확정된다.
- **원문을 함께 보관한다** — 구조화 결과 옆에 공시 원문(`bonusConditionText`)을 남긴다.
  번역이 틀렸는지 검수자가 대조할 수 있고, 사용자에게도 근거로 보여줄 수 있다.
- **두 흐름은 독립이다** — 흐름 1 이 없어도 흐름 2 는 돈다. 지금은 손으로 만든 데이터로 서비스가 동작하며,
  AI 파이프라인은 그 데이터를 자동으로 만드는 대체 경로로 나중에 붙는다.
